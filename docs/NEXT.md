# Next: a physically separate encrypted-policy demonstration

The new work in this PR is the [artifact-derived FHE size/cost table](fhe-fit.md), generated by [`tools/fhe_fit_table.py`](../tools/fhe_fit_table.py). It compares retained measurements, not a new encrypted run. The existing nonlinear and timing studies put client and server on the same Modal worker. The useful next experiment is smaller than another RL search: show the same fixed synthetic polynomial running with a client on one machine and an evaluator on another.

The [earlier affine CartPole reference](../artifacts/reference/modal-smoke-001.json) already records a local-entrypoint client and Modal evaluator with 25 matching encrypted steps. The missing demonstration here is remote execution of the **nonlinear** circuit, with explicit setup/network costs and borrowed hardware instead of paid Modal workers—not the first remote path anywhere in the repository.

## What the demonstration needs

1. **A second, compatible CPU machine.** Load the committed nonlinear policy and its serialized server bundle from [`modal-nonlinear-qmax2-002`](../artifacts/studies/modal-nonlinear-qmax2-002/). Concrete artifacts depend on architecture/runtime; use the pinned Concrete version and compatible x86-64 environment or explicitly recompile the identical policy. The original worker configuration requested 32 GiB RAM and 16 CPUs; that is a provisioned configuration, not a measured minimum. Do not infer that compilation or key generation fits this laptop. Check peak memory in a bounded trial on borrowed hardware first.
2. **Client-owned keys.** Generate a fresh secret key on the client, keep it there, and send only public evaluation keys and encrypted observations. The synthetic study measured 472,645,952 bytes of evaluation keys. Transmit them once per context and record that setup separately from per-request latency. Never transfer secret-key files or a serialized private context to the evaluator.
3. **An actual network boundary.** A local subprocess or two functions in one worker do not count. Use two hosts with a documented transport. Existing [`protocol.py`](../src/unseen_loop/protocol.py) binds request/response contents and context identifiers with HMAC; it is not a network server or a proof that the evaluator computed correctly. A local/remote entrypoint exists in [`modal_app.py`](../modal_app.py), but invoking Modal is paid compute and is not part of this $0 PR. A borrowed-host adapter would need to reuse these checks, transport the serialized ciphertext, and refuse clear fallback.
4. **A fixed, auditable comparison.** Reuse the declared 25-point input domain and repeat the same-input encryption checks. Keep the original artifact untouched. Save a new manifest with policy/bundle digests, runtime/CPU identifiers, host separation, fresh context identifier, every planned request and outcome, clear-reference agreement, and failure reasons. Do not publish secret keys or private real-world observations.
5. **Separated measurements.** Record compile/setup, key generation, one-time key upload, encryption, request upload, evaluator time, response download, decryption, end-to-end latency, and payload bytes. State whether context caching and warmup are enabled. A successful synthetic test would demonstrate remote execution for that circuit; it would not establish RL performance, safety, throughput, or malicious-server integrity.

## Time and cost estimate

Planning estimate, not a measured result: one to two working days to adapt and test borrowed-host transport, then a bounded CPU run capped at two hours. Paid-compute budget remains $0. Hardware access and its memory capacity are the missing prerequisites; this PR does not provision a service. The roughly 473 MB key transfer alone would take about 38 seconds over an ideal 100 Mbit/s link (bytes × 8 / link rate), before protocol overhead. Report the actual connection rather than presenting that estimate as latency.

Prefer this small demonstration to the full cloud matrix. If compatible borrowed hardware is unavailable, retain the current feasibility result and do not relabel colocated tests as remote privacy evidence.

## Source paths and execution status

- `policy.py`, `certificate.py`, and `fhe_backend.py` contain the polynomial/quantization idea, its narrow agreement proof, and Concrete execution.
- `shield/`, `ope/`, and `flagship/` are separate extensions. Their existing canaries and negative studies are not encrypted evaluation of the expanded RL champions.
- The newer ratio-lift WPDIS path is a source implementation with unit-test coverage, not a completed encrypted experiment. The diagnostic/pilot/confirmation stages described in the reproduction guide remain unexecuted.
- Historical Modal orchestration is retained for reproducing published runs. It is not required to regenerate the table or run the clear tests. Do not delete artifacts or assume an unexecuted path is dead merely because it is absent from the main CLI.

### Unused and historical paths

Repository reference searches found no internal callers for `PolynomialPolicy.scores`/`actions`, `MLPTeacher.action`, or `QuantizerSpec.bounds`/`dequantize`. They are unused convenience APIs, not evidence that the underlying policy, teacher, or quantizer implementation is dead. They remain unchanged because external callers are unknown. The active code uses quantized scores/actions and teacher `score` directly; the shield has a different, actively used quantizer.

`modal_independent_confirmation.py` is a historical replay asset, **not a path for another holdout**. Its second traversals of `ckks_raw` and `shield_raw` cannot collect failures after the generators have been consumed for successes. The reproduction guide already explains the empty failure-code lists. This PR does not rewrite that source or its historical result files. The newer ratio-lift path has actual callers; lack of a recorded encrypted run is not dead-code evidence.
